# 碎片工作台与头像参考库

## 页面与权限

- `/shards`：图片汇入、核对与图鉴；选择式神旁的搜索按钮支持繁体／简体／别名搜索及 Rarity 筛选。
- `/my-fragments`：选择自己的游戏账号，批量人工汇入或覆盖修改当前数量，填 0 清空。人工汇入区域可直接新增游戏账号（服务器默认「亞洲」），新增后自动选取；区域内显示当前写入账号。
- `/search-fragments`：按式神、Rarity、提供／需求及服务器寻找玩家。
- `/admin/samples`：Admin 审核、改绑、停用、删除头像参考。

全站需要登录。角色从 `players.role` 每次请求读取，只有 Admin 可以写图鉴和管理参考库，用户不能通过提交角色字段提高权限。图鉴新增／编辑支持繁体名、简体名、Rarity、HTTPS 图片路径、别名及排序；排序默认读取全表最大值加一（包括停用项目），输入框可编辑，冲突返回 409。停用图鉴保留历史资料。

图鉴卡片分别显示可提供总量及需求总量，点击头像查看玩家显示名、游戏账号、服务器和数量。查询接口不返回 Discord ID 或登录凭证。搜索最多返回 1000 条，需用筛选缩小范围。

## 当前数量

已执行 `migrations/004_fragment_management.sql`，创建私有、开启 RLS 的 `fragment_current` 和 `portrait_samples`。其他部署在基础 schema 与登录迁移后执行：

```powershell
python manage.py init-fragments
```

迁移从历史确认导入中按账号、式神、类别带入最新数量，重复执行不会覆盖已有的当前值。新增的当前数量以 `(game_account_id,shikigami_id,target)` 为主键；人工保存和图片确认保存都直接覆盖，不累加，不删除本次没有出现的项目。提供与需求各自独立。管理员没有跨账号写用户碎片的入口。

图片导入仍保留导入历史，同一批次重试不会再次写入当前值，因此不会把后来人工修改的数量改回旧值。图鉴总量只汇总启用玩家及游戏账号的当前数量，不累加历史导入。0 数量会在自己的整理页保留，搜索持有人时不展示。

## 头像参考

真实 OCR 完成后将原始卡片裁切与纯头像比对区域保存为待审核样本，关联上传者、任务、行号、OCR 文字及候选式神。比对区域采用头像内侧上部，避开边框、下方名字和数字。每位式神可保留多种皮肤、画质样本；只有 Admin 明确批准且式神启用的样本才会进入下一次识别。

目前环境只有 PostgreSQL 连接，没有 Storage 上传凭据，因此小尺寸 PNG 以 `bytea` 持久保存在 `portrait_samples`，单张上限 256 KiB；不保存完整长图，不使用 Render 临时目录承载参考库。图片接口仅 Admin 可访问。未来量增大时可将图片移到私有 Storage，并保留数据库的映射与审核字段。Admin 可以删除不用的裁切，控制存储量。

重复样本处理：上传时先检查启用式神的已批准参考，跳过归一化后相同或只有极小压缩差异的头像；仅相似但非重复的皮肤仍需审核。若 OCR 已指向另一个式神，保留该冲突样本。待审核列表及其计数也会排除队列中已有的重复图片，但不删除记录；参考图停用或删除后，隐藏的待审核样本可重新出现。「全部」和已审核历史不受此筛选影响。

每次上传加载最多 3000 个已批准样本，用 OpenCV 比较归一化颜色及边缘。按式神取最高参考分，满足较高阈值且领先第二候选时才辅助填入；与 OCR 精确名字冲突时保留 OCR 并标记核对。相同图片被错绑到不同式神会导致候选接近，不应自动选中。分数不是准确概率；数量仍由 OCR 与人工核对处理。

这不是训练 OCR 模型，也不能保证皮肤变化、严重模糊或裁切偏移下的识别率。已验证审核、停用、持久化及原样本读回比对；尚未用独立截图集测量新增匹配的准确率。
